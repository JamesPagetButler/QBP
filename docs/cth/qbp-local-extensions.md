# QBP-local extensions to the CTH schema

**Purpose:** single source of truth for every QBP-local extension to the canonical CTH inventory schema. Each row documents WHAT the local value means, WHY it exists, and WHEN/HOW it will round-trip to canonical CTH v0.3 values.

**Status:** v0.1 — first canonicalised record post-foundations-rebuild Phase 0 discovery (2026-05-22). Authored by qbp-implementor.

**Governing rule** (per `docs/cth/README.md` and `docs/workflows/pr7_conflict_routing_rubric.md`):

> Every QBP-local extension to a CTH inventory enum value MUST be either:
> 1. **Already canonical** in upstream `confluent-trust` (in which case it's not really a local extension), OR
> 2. **Tracked here with an upstream extension issue link**, AND co-signed by `@cth-implementor` on the QBP PR that introduces it.

If a value lands in `archive/cth-inventory/*.json` that isn't (1) or (2), the CI schema-lint rejects the PR.

**Rules.** Both grades are computed-not-declared: no human or script assigns them; a grade that looks wrong is fixed by new or corrected notary evidence, never by a hand edit (QBP#692 AC2/AC4). On anchors with no admissible evidence both are 0 (honest backfill, QBP#692 AC3; `PROOF-hessian` = 0 by absence — its `native_decide` is not kernel-clean and its python recomputation is `corroborated_by`-class, never an assistant). `pinned_sha` is NOT stored on the anchor (no ledger home at 0.3.5); the encoder derives it (one function, `pinned_sha_for`, the manifest rule above — superseding the earlier "blob of `proof_file`" wording: a single blob could not pin a cross-prover claim whose Coq/Lean evidence names a second QBP file) and the reconcile job re-derives it the same way; S and the per-file blobs are recorded in `analysis/692-pa-backfill/backfill-<date>.json`. Anchors with neither evidence nor a resolvable `proof_file` carry an empty, inert `pinned_sha` (nothing to be stale) and grade 0. **Target filter** (PR #695 Red Team C2; ruling 3e-refined item 4; cth live-test seq 2352, architecture seq 2353; §I4 round 2 live-test seq 2367 + Red Team re-check C5/N11 — final): an assistant counts toward an anchor only if it is the `lean4` assistant with a same-repo `evidence_ref` whose `#target` names that anchor's `lean_theorem` directly — a fully-qualified name equal to it verbatim, or a short (dot-free) name equal to its last dotted component **and** the ref's path equal to the anchor's `proof_file` (an unqualified name identifies the headline only inside the headline's own file) — or, for an assistant of a **different prover** than the headline's (Coq/Agda whatever its lemma is named, local or cross-repo), the record's correspondence block — `corresponds: true`, `checked_by` non-empty and not any assistant's `producer` — carries a structured `maps: [{target, lean_theorem}]` entry whose `target` equals this assistant's `#target` and whose `lean_theorem` equals this anchor's `lean_theorem`, both **verbatim** (Red Team N14: no short-name relaxation inside `maps`; `basis` is prose, never parsed; `maps` is encoder-side only — the engine's strict decoder never sees it; a name coincidence across provers is not a correspondence). **Kernel diversity is the maps criterion** (Red Team C6; architecture live-test seq 2372 + cth seq 2371; `maps_may_rescue`, one function): a correspondence attests that a *different* kernel checked the same statement, so `maps` may rescue only an assistant whose prover differs from the headline's — for a `lean_theorem` headline, never `lean4`. A Lean target that fails the direct match is dropped regardless of `maps`, same-repo or cross-repo: a Lean theorem that is not `lean_theorem` is a different Lean statement, and a map from it to the headline carries zero kernel diversity — it is a declared Lean→Lean derivation (a chain edge, seq 2338), not a cross-prover correspondence. Repo-locality is a provenance axis only (`cross_repo_evidence`, membership in S, staleness), never a maps-eligibility criterion. Anything else is dropped before the engine with report flag `target_not_headline:<assistant>`, so a cited companion theorem cannot lift a headline — by its name or by a declared Lean→Lean map — and a misfiled valid pair grades the headline 0; an anchor with no `lean_theorem` admits nothing by either route (flag `no_lean_theorem`, counted in the report — 22 at ledger 6.16.0, all `theory`/`theory-external`) (`scripts/encode_pa_from_evidence.py::filter_assistants_by_target` + `direct_target_match`, one rule, swappable by ruling). **Kernel collapse** (Red Team C7, issuecomment-5962978225; architecture ruling live-test seq 2386; Gemini concurs): because the vendored engine's `GradeClaim` counts clean *assistants*, not distinct kernels, the filter's survivors are then collapsed to the **first** admissible assistant per prover kind (`assistant` field) before the engine Claim is built and before the `proof_assistants` array is planned — every later same-kind survivor is dropped with report flag `same_kernel_duplicate:<kind>` — so `[coq, coq]` (two Coq lemmas, or one Coq entry listed twice) with no `lean4` grades 1, never 2, while Fano `lean4` + `coq` stays 2 (`collapse_to_one_per_kernel`, one function). The claim-source manifest S is taken over **all** of the record's same-repo `evidence_ref`s before the filter runs, so a dropped assistant never shrinks S or false-flags a survivor stale (Red Team C4); a cross-repo `@<commit>` must be a 7–40 hex sha (N8) and the explicit self-prefix `JamesPagetButler/QBP:` is local, compared case-insensitively as GitHub does (N9/N15). A same-repo `evidence_ref` whose path does not exist at the pinned master is a refusal naming the anchor, the claim and the evidence record file (N13) — dropped or kept, it is a member of S. `proof_assistants: []` is never written — when no assistant survives the key is omitted and the report flags `no_admissible_evidence`; the backfill report records the evidence store's identity (`git -C <evidence_dir> rev-parse HEAD` + `remote get-url origin`; a directory that is not a git checkout is recorded as `unknown (not a git checkout)`, never omitted — Red Team N2 on PR #697; the checkout's own path is never recorded — it is the `<evidence-repo>` base of the report's record paths, Red Team N7 on PR #703) and a `stale_proof_file` section naming every target anchor whose path-valued `proof_file` does not resolve at the pinned master (today: none; the two citation strings sit under `no_proof_file`); a v2 record whose `claim` is a ledger anchor that is not a target is listed under `evidence_for_non_target`, never graded silently. Anti-weakening: every drop between backfills is listed in the PR's before/after table. Rendered as the PA badge (local + effective + assistant names), QBP#692 AC5.

## Anchor fields (QBP#809 phase 1, measured_error/fit_sigma — 2026-11-14)

**Status:** QBP-local-awaiting-upstream since this PR (schema 0.3.7 → 0.3.8 — re-synced to real upstream 0.3.7 in this PR's fix round, confluent-trust#135 catch; the fit_sigma delta had mis-labelled itself "0.3.6" on a stale 0.3.5 base before that, colliding with upstream's real 0.3.6/0.3.7, cth-implementor issuecomment-6899400529). Beekeeper ruling 2026-11-13 ("adopt your recommendation") on #650's review: 64 anchors carry both a numeric `predicted_value` and `measured_value`; 44 had `measured_error`, 20 didn't (at filing time; the live count has since moved — see the PR for the current split); `status` was hand-set with no formula, and some stored errors are stale (`MEAS-alpha` ±0.02 vs PDG's current ±0.009). This section documents AC1 (the schema's fields) + AC4 (the computed script); AC2/AC3/AC5/AC6 (the real-literature backfill and its downstream consequences) are phase 2, tracked on #809 itself. Threshold refinement per inter#238 D3 ("fed-sigma-v1", qbp-oppenheimer, 2026-11-14/15): the two cap lines are named module-level constants, not inlined, because a future PR will reuse them. **Upstream extension issue:** confluent-trust#135 filed (AC1-AC5, targets 0.3.8) by @cth-implementor as part of its schema-axis co-sign on this PR. **Co-sign on the introducing PR:** given on the field content (cth-implementor issuecomment-6899400529).

| Field | Type | Meaning | Written by |
|---|---|---|---|
| `measured_error` | number | **1σ (68% CL)** symmetric measurement uncertainty on `measured_value`. Pre-existing CTH v0.3.0 field; this PR documents the convention it was always silently assumed to follow — no schema shape change. | hand-entered today (phase-2 backfill, AC2, will re-pin each value against a cited source) |
| `measured_error_plus` / `measured_error_minus` | number | **1σ (68% CL)** asymmetric upper/lower measurement uncertainty, for the (today: zero) anchors whose real error bar isn't symmetric. `compute_fit_sigma.py` uses the side **facing the prediction** when `measured_error` itself is absent — `measured_error_plus` if `predicted_value > measured_value`, else `measured_error_minus` — the uncertainty in the direction of the discrepancy, not a symmetrised average (T3 ruling, qbp-oppenheimer, issuecomment-6886846959). | hand-entered (phase-2 backfill, AC2) |
| `measured_source` | string, `minLength: 1` | The specific paper / PDG table+edition a `measured_value`+`measured_error` was pinned from. The non-empty-string floor is schema-enforced now; the citation's *actual content* (vs today's `"None"` / vague strings on some legacy rows) is AC2/AC3, phase 2. | hand-entered |
| `fit_sigma` | number \| null | `\|predicted_value − measured_value\| / sqrt(sigma_meas² + sigma_pred²)`, `sigma_pred = 0` until a prediction-error field exists. Rounded to 9 decimal places before storage/comparison (`FIT_SIGMA_ROUND_NDIGITS`) so IEEE-754 subtraction noise can't push an exact boundary value (e.g. `MEAS-alpha`'s mathematically-exact 5.0σ) across a cap line. `null` when no usable 1σ error is pinned, or the zero-denominator case (`measured_error == 0` with a nonzero discrepancy — e.g. `FLAG-ngc2683-mass-discrepancy`) is undefined; `fit_sigma_reason` then says why (`FitSigmaNeedsReason` schema conditional). | **computed only**, `scripts/compute_fit_sigma.py` — never hand-entered |
| `fit_sigma_reason` | string, `minLength: 1` | Present iff `fit_sigma` is null. | same script |
| `fit_history[]` | array of `{date, predicted_value, source, ledger_version, fit_sigma}` | **Append-only** log, one entry per evaluation run that actually changes something (including null evaluations — a future PR may read its length as a trials count, inter#238 D3). **The trials count is the number of entries with a distinct `predicted_value`**: a repeat run that reproduces the same `predicted_value` and `fit_sigma` as the last entry is idempotent and appends nothing, so it is not a trial; a phase-2 re-pin of `measured_error` that changes `fit_sigma` for the same `predicted_value` *does* append (it is new information about the measurement side), but is also not a new *predicted_value* trial (Gemini G1, PR #814 review, required-fix item 4). `source` is a best-effort pointer to the PR/spike/"leader" that produced the predicted value, read off whichever of `theory_citation`/`theory_url`/`theory_doi`/`foundation_batch` the anchor already carries; most of today's 64 candidates have none of those, so `source` is an honest `"unresolved — …"` placeholder pending AC2. The script refuses to replace an existing list — only extend it, and skips the append entirely on an idempotent re-run (`append_fit_history`/`history_is_idempotent`, tested against a literal-overwrite mutant and an unconditional-append mutant). **Since QBP#817 (variant A, frozen ledger version), `ledger_version` here is a tagged-by-shape string** (F8, cth-implementor's schema-axis call, revised 2026-11-18 after qbp-oppenheimer caught a squash/rebase problem with the first revision): a value matching `^\d+\.\d+\.\d+$` is a **pre-freeze row** — the issued semver directly, from back when `version` still bumped; any other value is a **post-freeze row** — this run's own fragment id (`"<issue>-<slug>"`, e.g. `"809-run-20261118-060000"`), which never matches the semver pattern (`issue` is a bare int, `slug` is never three dot-separated numbers). The frozen `version` field itself was rejected (every future entry would carry the SAME stale string forever); so was a commit sha (QBP allows squash/rebase merges, which leave a PR-branch commit unreachable from master — an append-only record citing it would cite a permanently dangling commit forever); so was the derived version (`ledger_version.current_version()`) — this PR's own D5 rule forbids citing an unmerged branch's derived version as issued, and baking one into a permanent append-only record would hard-code the exact collision this design prevents. The fragment id survives every merge mode (it names the tracked file's own identity, not a commit) and `scripts/ledger_version.py`'s `fragment_versions()` already resolves it to its issued derived version once it merges — read a post-freeze row's real version by resolving its fragment id through that function, never by reading `ledger_version` as a version string directly. `history_is_idempotent()` is unaffected (it only compares `predicted_value`/`fit_sigma`). | same script |

**The one-way status cap** (`fed-sigma-v1`, inter#238 D3): `fit_sigma > FIT_SIGMA_INCOHERENT_CAP (5.0)` caps `status` at `incoherent`-or-worse; `fit_sigma > FIT_SIGMA_MARGINAL_CAP (2.0)` caps it at `marginal`-or-worse; both thresholds are **strictly greater-than** (an anchor sitting at exactly 2.0σ or exactly 5.0σ does not trigger — resolves the issue text's `>`/`D3`'s `<`/`>` phrasing in favour of the issue's explicit strict operators, applied uniformly to both lines). "Or-worse" needs a severity ordering over the full `Status` enum, which has none upstream; `compute_fit_sigma.py`'s `SEVERITY` table orders it `converged < coherent < untested < marginal < incoherent < {refuted, falsified} < killed` (best to worst). `contested` sits **outside** this scale entirely (inter#238 R1: a logical-dispute state, not an empirical one) — it is never capped, only flagged via `target_cap_for()` so a report can still say what it *would* be. Ruled by @qbp-oppenheimer's theory-axis review (T2, issuecomment-6886846959): `untested` sits above `marginal`/`incoherent`; `refuted`/`falsified` tie (both terminal-bad); `converged` best, `killed` worst. The cap only ever **increases** an anchor's severity under this ordering; it never decreases it (an anchor already `killed` isn't un-killed by a later-recomputed low `fit_sigma`, and a currently-`incoherent` anchor with fit_sigma in the marginal band stays `incoherent`, not downgraded to `marginal`).

**Forward rule:** no other QBP-local field is added to `Anchor` for the fit_sigma mechanism without a row here and the upstream issue above. When the canonical confluent-trust PR lands, this row is marked canonical and the vendored schema resync follows `schema-change-propagation-checklist.md`.

## Frozen ledger bookkeeping (QBP-local process convention, not a schema change — QBP#817, 2026-11-16)

**This section documents a QBP *process* convention, not a field-value extension.** Nothing below changes `inventory.schema.v0.3.json`: `version`'s schema `description` stays byte-identical to upstream (cth-implementor, live-test seq5145 — editing a canonical field's description with QBP-local process prose is exactly the vendor-drift class that caused #814's version-collision incident). `version`/`changelog[]`/`last_updated` were always schema-untyped enough to carry this convention without a semver bump: no monotonicity, uniqueness or cross-field constraint on any of the three exists in the schema today (cth-implementor, seq5141).

**The problem this answers (QBP#817):** every PR that edited the ledger used to hand-write its own `version`/`changelog[]`/`last_updated` bump. Two PRs editing *completely disjoint* anchors still collided on these three shared fields, forcing a rebase and a full reviewer re-confirm (Red Team, Gemini, schema-axis, theory) for zero semantic reason — review cost scaled with how many ledger PRs happened to be open at once, not with how much content changed. Converged design (qbp-oppenheimer + qbp-architecture, QBP#817; beekeeper-ruled 2026-11-16, "go with A and add the changelog view").

**The rule, going forward:** a content PR never authors `version`/`changelog[]`/`last_updated` again. `scripts/cth_ledger_edit.py`'s `LedgerEdit.touch()` enforces this by construction — calling `touch("version")`/`touch("changelog")`/`touch("last_updated")` raises `ConfinementError` unconditionally, so this is not a convention a script could forget to follow. Instead, a content PR adds exactly one fragment file under `archive/cth-inventory/changes.d/<issue>-<slug>.json` (`scripts/ledger_fragment.py`), mirroring the ledger's own `ChangelogEntry` shape (`note`/`issue`/`slug`, plus `pr`/`encoder`/`touched_ids` for the generated view's columns) with `version`/`date` left `null` — the fragment *is* the entry of record; nothing re-authors its `note` later.

| What used to happen | What happens now |
|---|---|
| Each encoder hand-wrote `L["version"] = NEW_VERSION` and appended to `L["changelog"]` | The stored `version`/`changelog[]`/`last_updated` are **frozen at whatever they were when this convention took effect** — permanently inert history, never written again |
| "What version is the ledger at?" read `L["version"]` | `scripts/ledger_version.py` derives it: the frozen base, bumped once per merged fragment, **in the order those fragments actually landed on master** (`git log`, not filename order — a fragment never claims its own ordinal, which would reintroduce the exact collision this removes) |
| The changelog was hand-authored, in the ledger file | `scripts/generate_ledger_changelog_view.py` renders the changelog — one row per merged change: derived version · merge time · issue · PR · note · touched anchor ids. **Never committed** (D1 — see below): published to a `push`-to-master job's Actions summary, not to a tracked file |
| A PR's sign-off expired the moment *any* other ledger PR merged first | `scripts/ledger_bookkeeping_lint.py` is CI's backstop (defense-in-depth: `cth_ledger_edit` already can't produce the undetected case, but a hand-edited diff bypassing it, or an under/over-claimed fragment, still needs catching): frozen fields unchanged, exactly one fragment added when the ledger changed, `changes.d/` append-only, and the new fragment's `touched_ids` exactly matches what actually changed |

**What's deliberately *not* automated yet** (advisory, not gating — QBP#817 build order, PR-1 then a separate beekeeper-merged PR-2): the carry-by-semantic-hash rule (a review leg survives a pure rebase iff its hash over the changed records + non-generated file blobs, plus the 1-hop neighbour hash for theory/schema legs, is unchanged) is a design the directors converged on but is not yet wired into the merge-blocking parser — that gate change goes to the beekeeper separately. Re-running a specific PR's own encoder against a fresh master and diffing the result ("does the rebase reproduce exactly") also stays a documented, one-command-per-encoder manual recipe rather than a generic CI job: encoders have no shared CLI contract for a job to invoke generically. The *fragment's claim* against the diff IS automated (`ledger_bookkeeping_lint.py`'s fourth check) — it just can't re-run an arbitrary encoder on your behalf.

**Forward rule:** no script other than `scripts/ledger_version.py` / `scripts/generate_ledger_changelog_view.py` reads `L["version"]`/`L["changelog"]`/`L["last_updated"]` and reports it as the ledger's *current* state — they're historical values now, not live ones. A new consumer that wants "what version is this" calls `ledger_version.current_version()`.

**A derived version is authoritative only on master** (D5, qbp-architecture, QBP#817 PR-1 review, 2026-11-17). `ledger_version.py` derives order from `git log --first-parent -m` on the branch it's run against — on an open PR's own branch, that is the PR's own, not-yet-merged history, so two concurrently open PRs each legitimately compute the same "next" derived version (both honestly believe they're B+1). That is not a bug to fix; it is a fact about open PRs that was true before this design too. **Never cite a PR's own computed derived version as if it were issued** — cite the PR/issue number, or the commit sha, until it actually merges; only master's history fixes a derived version for good. The changelog view (below) is correspondingly never run against an open PR's branch for anything other than local sanity-checking — its published, citable output always comes from a push to master.

**The changelog view is never committed** (D1, qbp-oppenheimer, QBP#817 PR-1 review, 2026-11-17 — see `scripts/generate_ledger_changelog_view.py`'s module docstring for the full reasoning). `analysis/cth-ledger-changelog.md` does not exist as a tracked file; a content PR that hand-commits it fails `scripts/ledger_bookkeeping_lint.py`. The human-readable copy is published by a `push: branches: [master]` job straight to that push's GitHub Actions job summary — not durable (job summaries expire with log retention, 90 days by default); a genuinely durable publish target is the beekeeper's call.
